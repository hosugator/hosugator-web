## Context
Windows CI 러너가 실패했다. 원인은 코드가 아니라 호스트의 실행 통제 정책(Smart App Control)이었고, 그 판정이 **모델 기반 추론**이라 예측할 수 없었다. 하루 동안 재시도를 늘리고 표본을 늘리며 특징을 잡으려 했는데, 답은 표본을 늘리는 쪽에 없었다.

## Insight
### CI가 파는 것은 함의다

```
러너에서 통과  ⇒  현장에서 동작
```

CI의 가치가 전부 이 함의에 있다. 테스트를 돌리는 것 자체가 아니라, **통과했다는 사실로부터 현장 동작을 추론할 수 있다는 것**이 상품이다.

비결정적 요소가 검증 환경에 있으면 이 함의가 **양방향으로** 깨진다.

| | 이번 실례 |
|---|---|
| 거짓 초록 | 빌드 1차가 검증 PC에서 5/5 통과 → 출하했다면 다음 릴리스에서 현장 정지 |
| 거짓 빨강 | 문서만 고친 커밋이 5회 연속 실패 |

**거짓 초록이 더 나쁘다.** 빨강은 시끄럽게 틀리고 사람이 조사하지만, 초록은 조용히 틀리고 아무도 보지 않는다.

### 비결정적 속성은 표본으로 검증할 수 없다

```
결정적 속성   →  통과 = 항상 통과.  표본 하나로 함의가 성립한다
비결정적 속성 →  통과 = 이번엔 통과. 표본을 아무리 늘려도 함의가 안 생긴다
```

이게 내가 하루를 쓴 지점이다. 5회 재시도, 3회 재빌드, 208개 DLL 전수 검사를 했고, 그 결과로 알아낸 것은 "안전하다"가 아니라 **"표본으로는 알 수 없다"**였다.

관측 자체가 낭비는 아니었다 — 비결정적이라는 사실을 확정한 것이 결론으로 가는 길이었다. 다만 **그 사실을 확정한 뒤에는 관측을 멈추고 요소를 제거해야 했고**, 나는 계속 관측을 늘리려 했다.

### 대응은 제거하거나 결정적으로 만드는 것이다

```
제거한다      →  그 요소를 환경에서 없앤다
결정화한다    →  판정 근거를 파일 안으로 옮긴다 (예: 코드 서명)
```

시험을 더 하는 것은 어느 쪽도 아니다. **재시도는 통제 수단이 아니라 관측 반복일 뿐이다.**

검증이 이걸 그대로 보여줬다.

| 조건 | 결과 |
|---|---|
| 요소 있음 + 재시도 5회 | **0/5 성공** |
| 요소 제거 + 반복 5회 | **5/5 성공** (통과 건수까지 동일) |

같은 커밋, 같은 러너, 같은 조달 방식. 변수는 하나였다.

### 같은 원리를 이미 다른 곳에 적용해두고 있었다

돌아보면 이 프로젝트는 이미 이 원칙으로 움직였다.

| 조치 | 없앤 비결정성 |
|---|---|
| `uv.lock` 도입 | 설치 시점의 의존성 재해석 |
| `uv sync --frozen` | 락이 낡았을 때의 조용한 재해석 |
| `.python-version` 고정 | 환경 생성 시점의 인터프리터 패치 |
| 인코딩을 경계마다 명시 | 주변 로케일에 따른 디코딩 |

**인터프리터 조달과 호스트 실행 정책만 이 원칙 밖에 있었다.** 락파일을 도입한 이유가 "머신마다 다른 것이 설치되는 것을 막는 것"이었는데, 정작 인터프리터와 정책에는 적용하지 않았다.

### 그래서 검증 환경 구성 원칙

> **검증 환경은 결정적 구성요소로만 구성한다. 모델 기반이거나 외부 상태에 의존하는 것은 제거하거나 파일 안으로 고정한다.**

의심할 대상 목록은 대개 정해져 있다.

```
클라우드 평판 판정      SAC, SmartScreen, 안티바이러스 휴리스틱
외부 조회               라이선스 서버, DNS 의존 동작, 원격 레지스트리
시점 의존               "최신"을 가리키는 모든 것 (latest 태그, 범위 버전)
호스트 상태             설치된 도구 버전, 로케일, 정책
```

### 다만 "현장과 같게"와 충돌하는 것처럼 보인다

반론이 가능하다 — 현장에 그 요소가 있으면 러너에도 둬야 CI가 잡지 않겠냐는 것이다. **성립하지 않는다.** 비결정적 속성은 러너에 둬도 검증되지 않는다(위 참조). 현장에 그 요소가 있다면 선택은 둘뿐이다.

```
현장에서 제거한다        → 그러면 러너에서도 제거해야 대표성이 생긴다
결정적으로 만든다        → 서명처럼. 그러면 러너에서도 검증 가능해진다
```

**"러너를 현장과 같게"는 결정적 속성에만 적용되는 원칙**이다.

## Decision
러너 호스트에서 SAC를 제거했다. 설비 PC도 SAC 없이 셋업하기로 했으므로 러너가 대상 환경과 일치한다.

서명된 인터프리터를 조달해 "결정화"하는 안도 검토했고 실제로 효과가 있었다(번들 DLL 차단 1건 → 0건). 그러나 **배포물의 exe는 결정화할 수 없었다** — 우리가 서명하지 않는 한. 그래서 제거를 택했다.

**전환 조건**: 우리가 셋업하지 못하는 장비에 배포하게 되면 제거가 불가능하므로 결정화(코드 서명)로 전환한다.
