## Context
git 히스토리가 스쿼시되어 있어 `git blame`으로 특정 코드의 도입 경위를 추적 못 하고 파일 내용 자체를 증거로 재구성해야 했던 경험에서, "요즘은 커밋을 agentic AI가 정제해서 쓰는 경우가 많은데, 그럼 스쿼시가 불필요해지는가"로 대화가 이어졌다.

## Insight
### 스쿼시는 사실 서로 다른 두 가지 이득을 하나로 묶어서 판다

지저분한 개별 커밋("wip", "오타 수정", "되돌림")을 하나로 정리하는 것과, git 그래프/히스토리를 단순하게 유지하는 것은 별개의 문제인데, 스쿼시는 이 둘을 동시에 해결하는 대신 줄 단위 blame 세밀함을 통째로 희생한다.
즉 "이 변경 전체에 대한 책임/설명은 이 스쿼시 커밋 하나가 진다"로 재조직하는 트레이드오프다.

### AI가 커밋을 정제해서 쓰면 "지저분한 커밋" 문제는 줄지만, "그래프 복잡도" 문제는 그대로 남는다

이 둘은 별개의 문제라서, 하나가 해결됐다고 다른 하나도 자동으로 해결되지 않는다.
커밋 메시지 품질과 무관하게, 기능 하나당 여러 커밋이 수백 개 MR로 누적되면 `git log --graph`는 여전히 복잡해진다.

### 깔끔하게 분리된 커밋은 오히려 스쿼시 안 하는 쪽이 `git bisect`에 유리하다

버그를 이분탐색으로 찾는 `git bisect`는, 커밋이 잘게 나뉘어 있고 각각 독립적으로 빌드/테스트 가능할수록 정밀하게 원인을 좁혀준다. 
스쿼시하면 "이 MR 전체(수십 파일 변경) 어딘가"까지만 알 수 있는 반면, 안 하면 정확한 원인 커밋까지 좁혀진다.
AI가 커밋을 깔끔하게 분리해줄수록 이 이점이 커져서, 오히려 스쿼시의 필요성을 낮추는 방향으로 작용한다.

### 그래프 복잡도 문제의 실제 해법은 스쿼시가 아니라 리베이스다

Rebase and merge: 개별 커밋(AI가 깔끔하게 쓴 것들)은 그대로 다 남기되, merge commit 없이 일직선으로 재배치한다. 
"지저분한 커밋" 문제는 AI 정제로, "그래프 복잡도" 문제는 리베이스로 — 서로 다른 해법을 각각 적용하는 조합이 스쿼시 하나로 뭉뚱그리는 것보다 정밀하다.

### 리베이스는 "브랜치가 언제 병합됐는지"를 git 데이터 자체에서 지워버린다

merge commit은 부모가 둘인 특별한 노드로 "이 지점에서 브랜치가 합쳐졌다"를 `.git` 안에 영구히 기록하지만, 리베이스는 커밋을 그냥 재생(replay)해서 일직선으로 붙이므로 결과물만 보면 "누가 순서대로 main에 직접 커밋한 것"과 구조적으로 구별이 안 된다.

- 개별 커밋의 committer date는 리베이스 시점으로 바뀌지만(`author date`는 원래 작성 시점 유지), `git log` 기본 출력은 보통 author date만 보여줘서 이 단서가 눈에 잘 안 띈다.
- 실제 "언제 병합됐다" 정보는 GitHub/GitLab의 PR/MR 페이지에만 남는다 — 즉 순수 `.git` 데이터가 아니라 외부 플랫폼에 의존하게 된다.
- 플랫폼 접근 자체가 없어지면(레포만 클론해서 오프라인으로 여는 경우 등) 리베이스된 히스토리에서는 브랜치 경계를 원리적으로 복원할 수 없다.

### 절충안: `git merge --no-ff`나 태그로 통합 지점만 마커로 남긴다

개별 커밋의 세밀함(bisect용)과 "여기가 통합 지점"이라는 마커(merge commit이 주던 것)를 둘 다 가져가고 싶다면, fast-forward 가능한 상황에서도 강제로 빈 merge commit을 만들거나(`--no-ff`) 그 지점에 `git tag`를 찍어둔다. 완전한 리베이스만큼 그래프가 단순하진 않지만 순수 스쿼시보다 훨씬 세밀하다.
