## 1. 시스템 계층 구조 (호텔 비유)

컴퓨터 시스템은 각기 다른 역할을 수행하는 여러 층위(Layer)로 구성되어 있습니다.

| 층위       | 명칭                   | 비유            | 주요 역할 및 특징                                                             |
| :------- | :------------------- | :------------ | :--------------------------------------------------------------------- |
| **L5**   | **Application**      | 호텔 손님의 주문     | 비즈니스 로직, 사용자 인터페이스 (React, Vite 등)                                     |
| **L4**   | **Interface**        | 메뉴판 / 소통 창구   | **System Call**, API 등 층위 간 소통 규칙                                      |
| **L3**   | **Process / Thread** | 호텔 업무 단위      | **Process**: 독립된 단체 손님 (메모리 격리)<br>**Thread**: 단체 내 일꾼 (자원 공유, Worker) |
| **L2/1** | **OS / Kernel**      | 호텔 운영 정책 / 관리 | **Kernel**: 하드웨어를 제어하는 실질적 권력자 (사령탑)                                   |
| **L0**   | **Hardware**         | 호텔 시설 (물리 자원) | **CPU**(지배인), **RAM**(로비), **Disk**(창고)                                |

## 2. 주요 개념 상세

### 2.1. Kernel (커널)
- 운영체제의 핵심(씨앗)으로, 하드웨어 자원을 직접 관리합니다.
- 사용자 프로그램이 하드웨어를 직접 건드려 고장 내지 못하도록 중간에서 중재하며, **System Call**을 통해서만 요청을 받습니다.

### 2.2. Process vs. Thread
- **Process**: 실행 중인 프로그램의 단위입니다. 운영체제로부터 독립된 메모리 공간을 할당받습니다.
- **Thread**: 프로세스 내에서 실제로 일을 하는 실행 흐름입니다. 동일한 프로세스 내의 쓰레드들은 메모리를 공유하므로 통신이 빠르지만, 하나가 오류를 일으키면 전체 프로세스에 영향을 줄 수 있습니다.
- `btop`에서 확인한 `C0~C23` (24 Workers)은 이 쓰레드들을 처리할 수 있는 논리적 일꾼의 수입니다.

### 2.3. "Everything is a File" (리눅스 철학)
- 리눅스는 하드웨어 장치(마우스, 디스크), 네트워크 연결, 프로세스 상태 등을 모두 **파일(File)**이라는 통일된 인터페이스로 추상화합니다.
- 이를 통해 `cat`, `grep`, `lsof`와 같은 단순한 도구들을 조합하여 복잡한 시스템을 일관되게 관리할 수 있습니다.

## 3. 학습 인사이트
- **실력의 비례**: 소프트웨어 실력은 하드웨어에 대한 이해도와 비례합니다. 시스템의 층위를 이해하면 성능 최적화(동시성 관리)와 심층적인 디버깅(권한 및 자원 에러)이 가능해집니다.
- **Edge AI 관점**: 자원이 제한된 환경(Edge PC)에서는 하드웨어(L0) 사양에 맞춰 쓰레드(L3)와 메모리를 효율적으로 관리하는 것이 필수적입니다.

## 4. System Call — 계층 간 통신 방식

애플리케이션(L5)은 하드웨어(L0)를 직접 건드릴 수 없다.  
반드시 커널에 **요청**을 보내야 하며, 그 공식 창구가 System Call이다.

```
[Application]
     │  "파일 읽어줘" (read 함수 호출)
     ▼
[System Call Interface]  ← L4: 소통 창구
     │  커널 모드로 전환 (CPU 권한 상승)
     ▼
[Kernel]
     │  실제 디스크 접근
     ▼
[Hardware (Disk)]
     │  데이터 반환
     ▼
[Application]  ← 결과 수신 후 사용자 모드로 복귀
```

<!-- 💡 평소에는 Application이 사용자 모드(User Mode)에서 실행된다. System Call을 호출하는 순간만 커널 모드(Kernel Mode)로 전환되어 하드웨어 접근 권한이 생긴다. 이 전환 비용이 존재하기 때문에 System Call은 가능하면 줄이는 게 성능에 유리하다. -->

**대표 System Call 예시**

| System Call      | 하는 일                     |
| ---------------- | ------------------------ |
| `read` / `write` | 파일 또는 소켓 I/O             |
| `fork`           | 현재 프로세스를 복제하여 자식 프로세스 생성 |
| `mmap`           | 메모리 영역을 파일/장치에 매핑        |
| `ioctl`          | 장치 드라이버에 직접 명령 전달        |

## 5. 메모리 할당 — Stack vs Heap, 그리고 프로세스 격리

### Stack (스택)

함수 호출과 로컬 변수가 저장되는 영역. **크기가 컴파일 시점에 결정**된다.

```
main() 호출
  └── foo() 호출
        └── bar() 호출  ← 스택 최상단 (LIFO)
        bar() 반환      → 스택에서 제거
  foo() 반환            → 스택에서 제거
main() 반환
```

- 자동 할당/해제 — 함수가 끝나면 스택 프레임이 자동으로 사라진다.
- 매우 빠르지만 크기에 한계가 있다 (보통 수 MB). 초과 시 Stack Overflow.

<!-- 💡 재귀함수가 무한 반복되면 스택이 계속 쌓여 Stack Overflow가 발생하는 것이 바로 이 구조 때문이다. -->

### Heap (힙)

프로그래머가 **런타임에 명시적으로 할당**하는 영역. 크기를 실행 중에 결정한다.

```python
data = [None] * 1000000  # 런타임에 크기 결정 → Heap 할당
```

- 스택보다 크고 유연하지만, 직접 해제하지 않으면 **메모리 누수(Memory Leak)** 발생
- Python/Java 등은 **GC(Garbage Collector)** 가 자동 회수. C/C++은 수동 관리.

### 프로세스 격리 (Process Isolation)

각 프로세스는 OS로부터 **독립된 가상 주소 공간**을 부여받는다.

```
프로세스 A의 메모리 맵:      프로세스 B의 메모리 맵:
  0x0000 ~ 0xFFFF             0x0000 ~ 0xFFFF
  (A만의 독립 공간)            (B만의 독립 공간)
```

- A가 충돌해도 B에 영향이 없다. OS가 경계를 강제한다.
- 반면 같은 프로세스 내 **쓰레드들은 이 공간을 공유**하므로, 한 쓰레드의 버그가 전체 프로세스를 죽일 수 있다.

## 6. 가상화와 컨테이너의 층위적 위치

### VM (가상 머신) — 커널까지 복제

```
[Physical Hardware]
        │
[Hypervisor]  ← 물리 하드웨어를 중재 (VMware, KVM, Hyper-V)
   ┌────┴────┐
[VM 1]     [VM 2]
[Kernel 1] [Kernel 2]  ← 각자 독립된 커널 보유
[App 1]    [App 2]
```

- 완전한 격리: 다른 VM의 커널 버그가 나에게 영향 없음
- 무거움: 각 VM이 커널 + OS 전체를 들고 있으므로 메모리/부팅 비용이 큼

> 현재 사용 중인 WSL2가 이 방식. Windows 커널과 Linux 커널이 같은 하드웨어에서 동시에 실행된다.

### Container (컨테이너) — 커널 공유, 공간만 격리

```
[Physical Hardware]
        │
[Host OS Kernel]  ← 단 하나, 모든 컨테이너가 공유
   ┌────┼────┐
[C1]  [C2]  [C3]  ← 파일시스템/프로세스 네임스페이스만 격리
```

- 가벼움: 커널을 복제하지 않으므로 수십 ms 내 기동
- 격리 한계: 커널 취약점이 있으면 전체 컨테이너가 영향을 받을 수 있음

### 비교 요약

| 방식         | 커널  | 격리 수준   | 기동 속도 | 주 용도              |
| ---------- | --- | ------- | ----- | ----------------- |
| Bare Metal | 1개  | —       | 빠름    | 고성능 서버, Edge 디바이스 |
| VM         | N개  | 완전 격리   | 수십 초  | 멀티 OS, 보안 격리      |
| Container  | 공유  | 프로세스 격리 | 수백 ms | 마이크로서비스, CI/CD    |
