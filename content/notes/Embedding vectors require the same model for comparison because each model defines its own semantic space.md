## Context
align-ai LLM 에이전트 학습 중 RAG 구현을 위해 임베딩을 처음 다뤘다. 문서와 쿼리에 반드시 같은 임베딩 모델을 써야 한다는 제약의 이유를 파고들면서 임베딩 공간의 구조를 이해했다.

## Insight
### 임베딩 공간은 학습이 만들어낸 N차원 의미 좌표계다

임베딩 모델은 데이터를 고정 길이 숫자 배열로 변환한다. 각 차원은 특정 의미 축을 담당하지만, 어떤 의미인지는 학습 과정에서 블랙박스로 결정된다. 사람이 "차원 247은 부정적 사건을 나타낸다"고 지정한 것이 아니다.

```
"탐지 실패" → [0.12, -0.84, 0.33, ..., 0.07]  # 1536차원
"감지 안됨" → [0.11, -0.81, 0.35, ..., 0.09]  # 의미가 비슷 → 벡터도 비슷
"오늘 날씨" → [0.92,  0.14, -0.61, ..., 0.44]  # 의미가 다름 → 벡터도 다름
```

의미가 비슷하면 벡터가 비슷하게 나오는 이유는, 수십억 개의 문장 쌍으로 "같은 맥락에서 나오는 것은 가깝게"를 반복 학습했기 때문이다.

### U-Net 출력 벡터와 임베딩 벡터는 차원 설계 주체가 다르다

```
U-Net 출력 (사람이 설계):
  차원 0 → 배경 확률  ← 명시적, 해석 가능
  차원 1 → 라인1 확률
  차원 2 → 라인2 확률

임베딩 벡터 (학습이 설계):
  차원 247 → ???    ← 블랙박스, 해석 어려움
  차원 891 → ???
```

둘 다 벡터이지만, 전자는 정답이 각 차원의 의미를 규정하고, 후자는 학습 목표(의미가 비슷하면 가깝게)가 차원의 의미를 암묵적으로 결정한다.

### 임베딩 모델이 다르면 좌표계가 달라서 비교가 불가능하다

```
문서: text-embedding-3-small → 공간 A의 좌표
쿼리: text-embedding-ada-002 → 공간 B의 좌표

코사인 유사도를 계산해도 의미 없음 — 좌표계가 다름
```

RAG에서 문서 임베딩과 쿼리 임베딩에 반드시 같은 모델을 써야 하는 이유다. 더 좋은 모델로 교체할 때 저장된 문서 벡터 전체를 새 모델로 재임베딩해야 하는 운영 비용이 여기서 발생한다.

### 멀티모달 임베딩은 서로 다른 모달리티를 같은 공간에 놓는다

CLIP은 텍스트 인코더와 이미지 인코더를 학습해서 같은 벡터 공간에 투영한다.

```
"고양이 사진" (텍스트) → 벡터 [0.8, 0.3, ...]
🐱 (이미지)           → 벡터 [0.81, 0.29, ...]  ← 같은 공간, 가까운 위치
```

텍스트로 이미지를 검색하거나, 이미지로 관련 텍스트를 찾는 것이 가능한 이유다.
