## Context
오전에 PKM 정리를 집중적으로 하고 나서 오후에 코드 리뷰를 시작하려 했는데 눈에 안 들어왔다.
최근 7일 작업 분포를 분석해 보니 insight(합성·판단) 57%, study 30%로 고부하 작업이 대부분이었고, 저부하 작업 비중이 거의 없었다. 
업무 시간은 고정되어 있으므로 "피크가 지난 후반부를 어떻게 쓸 것인가"가 실질적인 질문이었다.

## Insight
### 의사결정 피로는 CRUD 프레임으로 이해된다

CRUD에서 R(Read)을 제외한 모든 작업 — Create(생성), Update(수정), Delete(삭제) — 은 판단이 필요하다. "이게 맞나?", "어떻게 바꿀까?", "지울까?"는 모두 의사결정이다. R만이 인지 예산을 소모하지 않는 작업이다.
기계적 수정(frontmatter 포맷 교정 등)도 판단 없이 규칙을 적용하면 낮은 부하처럼 보이지만, 내용을 이해하지 못한 채 형식만 고치는 것은 PKM 관점에서 가치가 없다. 결국 내용 이해가 동반되어야 하므로 완전한 저부하가 아니다.

### 피크 이후 시간은 세 가지 유형으로 활용 가능하다

**인풋 소화형** — 읽고 흡수만, 판단 없음
- PR 변경사항·파일 구조 파악 (코멘트·판단 없이)
- AI/ML 기술 블로그, 논문 초록 훑기
- 기존 zettelkasten 노트 읽기 (수정 없이)
- 이슈·티켓 목록 읽기

**처리 큐 소진형** — 이미 판단된 것 실행
- 슬랙·이메일 단순 답장 (Yes/No 수준)
- 티켓 상태 업데이트, 라벨 정리
- 이미 결정된 작업의 boilerplate 작성

**준비형** — 내일 오전 고부하 작업의 마찰 제거
- 내일 리뷰할 PR 파일 목록과 PR 설명만 읽어두기
- 다음 학습 주제 검색만 해두기 (판단 없이)
- 내일 할 작업 목록 작성

### 코드 개발의 오전/오후 배치 기준은 설계 완료 여부다

코드 개발도 코드 리뷰와 동급의 고부하 작업이다. AI에게 위임하면 본인은 R에 가까워지지만, 부하가 사라지는 게 아니라 리뷰 시점으로 이동할 뿐이다.

- **설계 완료 → 오후 배치 가능**: 판단 없이 AI에게 지시만 하면 되는 구현. 오후에 작성하고 다음 날 오전에 리뷰하면 맥락이 살아있어 진입 마찰이 낮다.
- **설계 미완 → 오전 배치**: 무엇을 어떻게 만들지 결정하는 것 자체가 고부하. 오후에는 적합하지 않다.

### 준비형이 가장 레버리지가 높다

인풋 소화형은 당장 아웃풋이 없어 "시간 낭비"처럼 느껴질 수 있다. 처리 큐 소진형은 보람이 있지만 긴급하지 않으면 오전에 해도 된다. 준비형은 내일 오전 판단 작업의 진입 마찰을 낮춰서, 피크 시간을 실제 판단에만 쓸 수 있게 만든다. 오늘 오후 30분이 내일 오전 1시간을 살린다.
