## 핵심 전제

AI 에이전트에게 구현을 위임하는 시대로의 전환은, 이해의 기준 자체를 바꾸는 것이지 이해를 포기하는 것이 아니다.  
불안의 원인은 능력 부족이 아니라 새로운 기준의 부재다.

---

## 과도기적 혼선의 실체

"구현을 직접 짜는 세대"에서 "구현을 위임하는 세대"로 전환하는 과정에서 기존 기준이 무너진다.

```
기존 기준: 내가 짠 코드 → 줄 단위 이해 → 책임 가능
새로운 상황: AI가 짠 코드 → 어느 수준까지 이해해야 하는가?
```

이 기준이 명확하지 않은 상태에서 위임이 먼저 일어나면 불안이 생긴다.  
불안의 실체는 "내가 모른다"가 아니라 "얼마나 알아야 하는지를 모른다"다.

---

## 새로운 이해 기준

코드 한 줄·변수명 암기는 더 이상 유효한 이해의 기준이 아니다.

| 구분    | 기존 기준       | 새로운 기준     |
| ----- | ----------- | ---------- |
| 이해 단위 | 함수, 변수명     | 원리, 설계 의도  |
| 검증 방법 | 코드를 처음부터 설명 | 한계와 전제를 설명 |
| 책임 범위 | 코드 작성       | 판단과 방향 결정  |

직접 짠 사람도 일주일 후엔 변수명을 기억하지 못한다. 코드는 항상 열어봐야 한다. 그게 정상이다.  
원리를 이해하면 코드를 보지 않고도 "체크포인트 경로가 같으면 모델을 캐싱해서 반환한다"고 대답할 수 있다.

---

## 보고·발표에서 실제로 오는 질문

코드 레벨 질문은 코드 리뷰에서 온다. 보고와 발표에서 오는 질문은 다르다.

```
실제 질문:
  "왜 추론이 빨라졌나요?"        → 원리 이해로 대답 가능
  "CPU로 전환하면 현장에서 쓸 수 있나요?" → 설계 이해로 대답 가능
  "동시에 여러 명이 쓸 수 있나요?"  → 한계 파악으로 대답 가능

오지 않는 질문:
  "pollRef가 왜 useRef로 선언됐나요?"  → 코드 리뷰
  "이 변수명은 왜 이렇게 지었나요?"    → 코드 리뷰
```

---

## 진짜 위험 지점 — 구현의 한계를 모르는 것

코드를 모르는 것보다 이 시스템이 무엇을 못 하는지를 모르는 것이 실무에서 치명적이다.

예시:
- 추론 Worker가 요청을 순차 처리(블로킹)한다는 사실을 모르면 "동시 사용 가능하다"고 잘못 답한다
- 이건 코드를 외워서 아는 것이 아니라, 설계를 이해해서 아는 것이다

책임의 경계선: "변수명을 아는가"가 아니라 "이 구현의 전제와 한계를 설명할 수 있는가"

---

## 전동공구 비유

전동공구가 생겼다고 목수가 나무의 결과와 하중 계산을 몰라도 되는 것은 아니다.

```
AI가 대신하는 것:  대패질 (구현 동작)
여전히 사람 몫:    어느 방향으로 깎을지 (설계 판단)
                  어느 나무를 쓸지 (기술 선택)
                  이 구조가 하중을 버티는지 (한계 파악)
```

---

## 올바른 위임의 조건

불안 없이 위임하려면, 위임 전에 이것들이 확립되어 있어야 한다:

1. 왜 이 방식을 선택했는가 (설계 의도)
2. 어떻게 동작하는가 (핵심 원리, 추상화 수준)
3. 무엇을 못 하는가 (전제와 한계)

이 세 가지를 말할 수 있으면, 코드를 줄 단위로 외우지 않아도 책임질 수 있다.  
이 세 가지 없이 위임하면, 기능은 완성되어도 불안이 남는다.

---

## "직접 구현해야 배운다"는 전제에 대한 반론

역설처럼 보이지만, 역설이 아니다.

위임을 잘 하려면 코드 레벨 어휘력(어떤 라이브러리, 어떤 패턴, 캐시인지 큐인지)이 필요하다.  
그 어휘력을 쌓으려면 직접 구현해야 한다.  
그런데 직접 구현하면 에이전트를 왜 쓰는가?

해소 방식: 배움의 경로를 "직접 작성"이 아니라 "깊은 관여(deep engagement)"로 재정의하면 풀린다.

- AI가 짠 코드에 "왜 이걸 썼나"를 물어보는 것
- "GIL이 있는데 어떻게 GPU가 95%인가"를 이해하는 것
- "이건 Promise queue 패턴이네"라고 읽히게 되는 것

이 모두가 코드 레벨 학습이다. 저자가 아닌 독자로서의 학습이지만, 원리 이해 측면에서는 동등하다.

## 에이전트 시대의 코드 리뷰

코드 리뷰는 사라지지 않는다. 질이 바뀐다.

```
이전: "이 변수명이 맞나?" "이 로직이 올바른가?"
이후: "이 캐싱 전략이 이 요청 패턴에 맞나?"
      "이 큐 구현이 동시성 요구사항을 충족하나?"
      "이 아키텍처 선택의 전제가 우리 시스템에 성립하나?"
```

이 질문을 던지려면 패턴의 이름과 쓰임새를 알아야 한다.  
변수명은 몰라도 되지만, "이게 왜 큐인가"는 알아야 한다.  
그것이 에이전트 시대 코드 리뷰어의 어휘력이다.

---

## 실질적 학습 경로

전체를 직접 짜는 것(효율 낭비)과 패시브 위임(학습 없음) 사이의 경로:

1. 질문하며 읽기: AI 코드를 받을 때마다 "왜 이 패턴인가"를 물어보고 이해한다
2. 핵심 부분만 직접 짜기: 함수 하나, 엔드포인트 하나 단위로 직접 구현해본다
3. 반복: `callInferWorker()` 같은 큐 패턴을 한 번이라도 직접 짜보면, 다음에 AI가 비슷한 구조를 만들었을 때 읽힌다

ADR에 코드 레벨 의도를 못 쓰는 것은 경험 부족이 맞다.  
그것을 채우는 경로는 전체를 직접 짜는 것이 아니라, 질문하며 읽기 + 핵심 부분 직접 짜기의 반복이다.
