## 계층별 Prefix 권고

[[3계층 문서 아키텍처 - 관심사별 SSOT 분리 원칙]]의 각 계층에 prefix+번호를 붙이면 문서 성격을 파일명만으로 식별할 수 있다.

| 계층 | 권고 Prefix | 예시 | 근거 |
|:---:|:---|:---|:---|
| **1. Domain Docs** | `SPEC-NNN` | `SPEC-003-inference-pipeline.md` | 기술 명세의 산업 표준어. 도메인 분기가 필요하면 `ARCH-`, `API-`, `ML-`, `DATA-`로 세분화 |
| **2. Process Records** | `ADR-NNN` | `ADR-012-patchcore-over-efficientad.md` | Michael Nygard(2011) 제안 이후 Google·AWS·Spotify가 채택한 사실상 표준 |
| **3. Communication Artifacts** | `RFC-NNN` 또는 `BRIEF-NNN` | `RFC-005-lmr-phase1-proposal.md` | RFC: 이미 현업 표준어, ADR과 같은 3글자, 협의 문서임을 직관적으로 전달. BRIEF: 비기술 이해관계자(경영진, 운영팀)가 주 독자일 때 더 직관적 |

### 번호 채번 원칙
- 계층 내 전역 시퀀셜 증가 (ADR-001, ADR-002 ...). 결번 허용, 재사용 금지.
- 0-패딩 자리수는 예상 문서 수에 맞게 결정: 3자리(최대 999), 4자리(최대 9,999). 파일 시스템은 문자열을 사전순으로 정렬하므로 패딩 없으면 `ADR-9`가 `ADR-10` 뒤에 온다.
- SPEC은 도메인 접두어 조합 가능: `SPEC-ML-003`, `SPEC-API-007`.

## 현업 프레임워크 비교

### Spotify RFC → ADR (2-단계 모델)

```
RFC (공개 협의) → ADR (결정 기록)
```

3계층과의 관계:
- RFC ≈ Communication Artifacts (Layer 3)
- ADR ≈ Process Records (Layer 2)
- **Domain Docs 계층이 없다** — 결정 후 코드베이스가 암묵적으로 SSOT 역할을 대신함

**왜 현업은 ADR-only를 선호하는가:**

ADR-only가 단순해 보이지만, 실은 유지비용 때문에 Domain Docs를 의도적으로 포기한 선택이다.

| 문제 | ADR-only | Domain Docs 추가 시 |
|:---|:---|:---|
| 구현 전 상태 | ADR에 "미구현" 표기로 처리 | SPEC이 유일한 SSOT — 유용 |
| 구현 후 상태 | 코드가 SSOT, ADR은 "왜"의 기록 | SPEC이 코드와 동기화 의무 발생 |
| 도메인별 접근 | ADR 인덱스 파일로 보완 가능 | SPEC에서 직접 접근 가능 |
| 유지 비용 | ADR은 추가만 (append-only) | SPEC은 변경마다 업데이트 필요 |

핵심 비대칭: **ADR은 append-only**다 — 한 번 쓰면 수정하지 않는다. SPEC은 시스템이 바뀔 때마다 갱신해야 한다. 빠르게 변하는 프로젝트에서 SPEC은 ADR보다 빠르게 부패(rot)한다.

**ADR 도메인 접근 문제의 현업 해결책:**  
Domain Docs 없이도 도메인별 접근은 다음으로 해결한다:
- ADR frontmatter에 태그 추가 (`tags: [ml, anomaly-detection]`)
- `DECISIONS.md` 인덱스 파일 — "ML 관련: ADR-005, ADR-012, ADR-023"
- 파일명에 도메인 포함: `ADR-012-ml-patchcore-selection.md`

**Domain Docs가 정당화되는 시점:**  
- 구현 전 설계 단계 (코드 SSOT가 아직 없음)
- 독자 범위가 넓을 때 (ML 엔지니어 + 데이터 엔지니어 + 기획자 혼재)
- API 계약, 데이터 스키마처럼 코드에서 추출하기 어려운 명세

트레이드오프:
- (+) RFC가 팀 전체에 공개되어 참여 폭이 넓음
- (-) Domain Docs 부재로 시스템 현재 상태를 알려면 코드와 ADR을 모두 읽어야 함
- (-) RFC는 소비 후 종료가 아니라 아카이브로 남아 stale 문서가 누적됨

### Google Design Docs (단일 문서 모델)

```
Design Doc (Problem + Architecture + Trade-off + Review) → 코드
```

3계층과의 관계:
- Process Records + Communication Artifacts를 하나의 문서에 통합
- Domain Docs는 별도로 관리하지 않고 코드베이스에 위임

트레이드오프:
- (+) 문서 수가 적어 관리 부담 낮음
- (+) 협의 맥락과 결정이 같은 파일에 있어 추적이 쉬움
- (-) "왜 결정했는가"와 "어떤 피드백이 있었는가"가 뒤섞여 나중에 읽기 어려움
- (-) 계층 간 SSOT 경계가 없어 문서 간 내용 중복 판단을 매번 해야 함

### Divio / Diataxis (사용자 관점 4분면)

```
Tutorials | How-to Guides | Reference | Explanation
(학습)      (실행)          (조회)       (이해)
```

3계층과의 관계:
- **전혀 다른 축** — 독자(user-facing)를 기준으로 분류하며, 조직 내부 거버넌스(결정 기록, 이해관계자 협의)를 다루지 않음
- 오픈소스 라이브러리나 제품 문서에 적합. 내부 엔지니어링 문서 구조로 쓰기에는 부적합

트레이드오프:
- (+) 독자 경험 최적화에 탁월
- (-) Process Records와 Communication Artifacts 개념 자체가 없음

### Confluence Wiki (계층 없는 자유형)

스페이스(Space) → 페이지(Page) 트리 구조. 계층 구분 없이 조직별로 자유롭게 구성.

트레이드오프:
- (+) 진입장벽 낮음. 어떤 형식의 문서든 수용
- (-) SSOT 소재가 불명확. 같은 내용이 여러 페이지에 산재
- (-) 문서 생명주기 개념이 없어 stale 페이지가 무한 누적
- (-) 검색에 의존하게 되어 조직 규모가 커지면 찾기 어려워짐

## 3계층 구조의 차별점

현업 프레임워크 대부분이 갖지 않는 두 가지 원칙:

**1. Communication Artifacts의 명시적 생명주기**  
Brief는 `draft → 협의 → Domain Docs 반영 → closed`로 종결된다. 대부분의 현업 방식은 생명주기 없이 문서를 아카이브로만 남겨 stale 누적을 방치한다.

**2. 계층별 SSOT 할당**  
각 계층이 서로 다른 질문의 SSOT다 — 시스템 상태(SPEC), 결정 맥락(ADR), 협의 이력(BRIEF). 같은 사실이 여러 계층에 표현되어도 SSOT 위반이 아니다. 현업은 SSOT를 '내용 단위'로 논쟁하다가 중복 판단 비용이 커진다.

## SPEC의 Stale 문제와 미해결 트레이드오프

RFC와 ADR은 각자의 stale 문제를 구조적으로 해결한다:
- RFC: `closed` 생명주기로 소비 후 종결
- ADR: append-only — 수정하지 않으므로 rot이 없음

SPEC(Domain Docs)은 이 두 계층과 달리 **시스템이 변할 때마다 갱신 의무가 발생한다.** 코드가 바뀌면 SPEC도 손으로 따라 써야 하는 **dual-write 구조** 자체가 rot의 근원이다.

이를 코드 설계에 대입하면 SPEC은 God Class 안티패턴을 막아주지만, 문서를 관심사별로 분리한 만큼 각 문서가 독립적으로 stale해질 위험이 커진다. 피할 수 없는 트레이드오프처럼 보인다.

### 현업의 해결 방향

**방향 1 — SPEC을 코드에서 자동 생성 (Docs-as-Code)**  
dual-write를 원천 제거하는 방식이다. 코드가 바뀌면 SPEC도 자동 갱신된다.

| 대상 | 자동 생성 도구 |
|:---|:---|
| API 명세 | FastAPI → OpenAPI, Swagger |
| 데이터 스키마 | ORM → ERD 자동 추출 |
| 아키텍처 다이어그램 | Backstage, Structurizr |
| 인터페이스 계약 | protobuf, GraphQL schema |

한계: 코드로 표현되지 않는 것 — 설계 의도, 비즈니스 제약, 구현 전 설계 — 은 자동 생성 불가.

**방향 2 — SPEC의 범위를 "코드로 표현 불가능한 것"으로 최소화**  
구현 세부사항은 코드에 위임하고, SPEC에는 다음만 남긴다:
- 구현 전 설계 의도 (pre-implementation)
- 코드가 표현하지 못하는 비즈니스 제약
- 인터페이스 계약 (서비스 간 경계)

이 둘의 공통 원칙: **SPEC이 코드의 그림자가 되지 않도록.** SPEC이 코드를 산문으로 재서술하는 순간 rot이 시작된다.

### 결론 — 어쩔 수 없는 트레이드오프인가

RFC·ADR은 명확히 필요하다 — 협업/개발 용도로 관심사·소통 언어·목적이 명확히 다르다.  
SPEC은 God Class를 막지만 유지비용이 있다. 이 비용을 0으로 만들 수 없다면 최소화하는 두 전략이 현실적 해답이다:

1. 자동 생성 가능한 SPEC은 코드에서 생성
2. 수동 SPEC은 "코드가 말하지 못하는 것"만 담아 표면을 좁힘

Google Design Doc의 단순함은 이 유지비용을 **문서 수를 줄임으로써** 해결한 것이다. 독자 결합(audience coupling) 문제는 감수한다. 3계층은 독자 결합을 해소하는 대신 유지비용을 분산한다 — 어느 쪽이 유리한지는 팀 규모와 독자 다양성에 달려 있다.

**핵심 재확인 (2026-04-24):**  
ADR을 Google Design Doc처럼 시스템 상태의 SSOT로 삼으려는 시도가 이 구조의 주된 혼동 원인이다. 각 계층의 역할을 정확히 구분하면:

```
RFC/Brief  →  ADR       →  SPEC
협의 도구      결정 audit     시스템 상태 SSOT
(to closed)   (to closed)   (living)
```

SPEC만이 살아있는 SSOT다. ADR과 RFC는 SPEC을 갱신하는 촉매이며, 역할이 끝나면 닫힌다.
