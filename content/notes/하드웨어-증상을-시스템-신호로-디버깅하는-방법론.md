## insight
하드웨어처럼 보이는 문제도 OS 레이어의 신호를 따라가면 소프트웨어로 해결할 수 있다. 중요한 것은 **증상이 아니라 신호의 흐름**을 추적하는 것이다.
이번 Philips 모니터 USB-C 자동 전환 문제에서 이것을 직접 경험했다. 처음에는 모니터 설정 문제로 보였지만, 실제 원인은 GNOME DPMS가 NVIDIA GPU의 DisplayPort 신호를 완전히 끊는다는 것이었다.

## 신호 추적 순서 (나의 실전 패턴)

```
journalctl (이벤트 발생 시점 확인)
  → xrandr (현재 출력 상태 확인)
  → dbus-monitor (세션 이벤트 감지)
  → 로그 메시지 (타이밍 문제 발견)
```

이 순서가 효과적인 이유는 "무언가 일어났다"는 사실 → "어떤 상태인가" → "왜 그 순서인가"로 범위가 좁아지기 때문이다.

## 발견한 하드웨어-소프트웨어 매핑 (Gigabyte AERO X16 기준)

- USB-C 포트 → NVIDIA dGPU 경유
- HDMI 포트 → AMD iGPU 경유
- GNOME DPMS 활성화 시 NVIDIA GPU가 DP 신호를 완전 차단 (모니터가 소스 없음으로 인식)

이 포트-GPU 분리 구조를 몰랐기 때문에 오래 방치했다. 하드웨어 스펙이 아니라 실제 신호 흐름을 xrandr로 확인한 뒤에야 원인을 특정했다.

## 패턴 일반화

하드웨어 증상을 마주쳤을 때:
1. 증상이 발생하는 **OS 이벤트**를 먼저 특정한다 (DPMS off, session lock, suspend 등)
2. 해당 이벤트와 연결된 **시스템 신호 경로**를 역추적한다 (D-Bus → DRM → xrandr)
3. 소프트웨어 레이어에서 개입 가능한 지점을 찾는다

## 추가 교훈 (2026-05-08)
OS 레이어에서 모든 소프트웨어적 수단을 시도해도 해결 안 될 때, **하드웨어 OSD 설정**을 먼저 확인했어야 했다.
이번 케이스에서 폴링 방식, Mutter API, DRM sysfs, ucsi_acpi 리로드, VT 전환, DDC/CI 등 반나절을 소모했지만 결국 모니터 OSD 한 항목("USB 대기 모드 켜기")이 해결책이었다.
USB-C는 디스플레이 포트이면서 동시에 전원/데이터 포트이기 때문에, 모니터의 USB 절전 정책이 DP Alt Mode 유지 여부를 결정한다. 이 레이어는 OS 신호 추적만으로는 도달하지 못한다.

**수정된 디버깅 순서:**
```
OS 이벤트 → 시스템 신호 경로 추적
  → (소프트웨어 개입으로 해결 안 될 때) → 하드웨어 OSD 설정 점검
  → (그것도 안 될 때) → 드라이버/펌웨어 버그 의심 후 리포트
```
